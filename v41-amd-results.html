AMD Strix Halo — DeepSeek V4.1 Flash engines

Which inference engine runs DeepSeek V4.1 Flash best on one Ryzen AI Max+ 395 (Radeon 8060S, gfx1151, 128 GB). Every candidate that could be run was run on the box; the KPIs are prefill and decode tok/s, single user first, four parallel users as an auxiliary metric. Measured 2026-10-03.

Verdict. kyuz0's ds4 ROCm branch with resident/missing MoE split enabled (feat/rocm-deepseek41-halo + DS4_ROCM_SELECTED_SPLIT=1) runs V4.1 Flash on this box: ~9 tok/s decode (+35% over baseline), flat across context, and prefill rising from ~22 to 125 tok/s with prompt size. The split optimization (from kyuz0/ds4 PR #4, commit 546aa99) is production-ready: quality is identical (89.3% top-1, ×1.18 PPL), and it is a single-user engine here: four parallel users get less aggregate throughput than one.
Why every engine streams from SSD. V4.1 Flash has a 552B backbone. The smallest builds are 365.7 GB (ds4 Q2: 152 GiB main weights + 189 GiB Engram tables) and 264.5 GB (llama.cpp Q2_K). Neither fits in ~122 GiB of usable RAM. V4.1 is not V4-Flash-0731.

2Method

One engine-neutral streaming client against each engine's OpenAI-compatible server, so every number is measured the same way.

  • Prefill tok/s = prompt tokens ÷ time to first token. Decode tok/s = (completion tokens − 1) ÷ (last token − first token).
  • 256 output tokens, temperature 0, thinking off; a unique nonce opens every request so nothing is served from a prefix cache; one warm-up request excluded.
  • Short ≈ 940 tokens · medium ≈ 6,580 tokens · long = 15,626 tokens: the captured first request of a real Claude Code session (system prompt, 20 tool schemas, first user turn), replayed verbatim. Sessions with MCP servers can reach 20–51K.
  • ds4: --ssd-streaming --ssd-streaming-cache-experts 76GB --ctx 20480; 4 users via --batched-session 4. Single-user rows: two runs each.

On ROCm with SSD streaming, ds4 serves batched sessions in order rather than batching them natively, and four contexts churn the SSD expert cache. After the first 2,048-token chunk, concurrent prefill falls to ~6.5 tok/s per session. Aggregate throughput with four users is below a single user's.

Reading it. Q2 is about 18% worse in perplexity overall. The loss depends far more on task than on context length: code keeps 91–97% agreement out to 32K, while non-English creative writing drops to 70–80%. For a coding agent, Q2 is a reasonable trade on a 128 GB box. Cross-check: on the general suite this ROCm scorer gives 90.2% / MAE 0.227, close to the fork's published ROCm 90.48% / 0.2196. The reference is a hosted service, not bit-identical to the released weights, so part of the gap is reference noise; the long suite rests on 64 scored tokens per case.

6Expert-cache tuning

V4.1 Q2 cannot be resident here (151.8 GiB of main weights against ~122 GiB of RAM), so ds4 keeps the static weights plus a cache of experts in GPU memory and reads misses from SSD. Single user, kyuz0 ds4, tok/s; two runs each.

Reading it. 84 GB is the best setting: about +3% decode, close to noise, with no prefill loss. 88 GB costs 13–25% prefill, probably because less memory is left for prefill's expert batches, and produced one decode outlier (4.66 tok/s, 1.4 GB/s SSD reads, no swapping). Cache size is not the lever: only about half the expert weights can ever be cached, so every token still misses many experts. ROCm 10.0 or a second machine is.
