On an M1 Ultra 128 GB: 42.5 tok/s decode, 888 t/s prefill at 512 tokens. The weights are on internal NVMe and the rate is measured with llama-bench on the exact catalogued file. It is marked provisional because the host was not idle and decode spread 10% across three processes, so 42.5 is a floor at the default thread count rather than a quiet-box rate.

A 9B dense fine-tune of Qwen/Qwen3.5-9B published by DavidAU, in GGUF form, with a multi-token-prediction (MTP) layer. Local Mind catalogues the MTP Q4_K_M build and measures it; the upstream repository also ships non-MTP quants and vision projectors that this entry does not cover.

The architecture line is read from the GGUF header rather than from the publisher's prose, by HTTP range request over the first 30 MB of the file. That read is also what establishes it is dense: the header carries no expert_count or expert_used_count, so the row prices on its whole 6.50 GiB per token rather than on an active-expert fraction.

Three separate processes, each at llama-bench -p 512 -n 128 -r 3 -ngl 99, on stock llama.cpp build b29c606e2 (10964), default thread count (16), the catalogued file on internal NVMe, fully offloaded. Separate processes rather than one process with more repetitions, because this site's earlier lesson is that run-to-run variance is larger than repetition-to-repetition variance and a single process hides it. The quoted figures are the medians; the ranges are shown above rather than averaged away.

Two conditions keep this row provisional, and both move the result by more than the differences worth reporting:

  • The host was not idle. Two unrelated llama-server processes held about 93 GB resident on this 128 GB machine while the benchmark ran. Decode is resident after load, so it is the less exposed of the two figures, but the 10% spread across identical runs is the cost of the load.
  • Thread count matters here more than on a plain dense model. The same file at -t 8 measured 54.0 tok/s decode against 41.8–46.1 at the default 16. That is the hybrid linear-attention blocks doing work the thread count changes; it is why the row quotes the default configuration and calls the figure a floor rather than a peak.

A quiet-box re-measurement will replace this badge when the machine is free. Until then the app's own estimate for this row is the same measured floor, and it is marked modelled in the app because the app has not run the file itself.

MTP, and what this number is not

The catalogued file is the MTP variant: the header declares qwen35.nextn_predict_layers = 1, and the repository ships the same quants without that layer beside it. llama-bench wires no drafter, so the 42.5 tok/s is ordinary decode on the MTP file and does not depend on speculative decoding; the nextn block is not read per token unless a drafter is enabled. The publisher's own figures — about 130 t/s regular and up to 185 t/s MTP for Q4_K_S on an RTX 5090 under LM Studio — are his, on different hardware and a different engine, and are not carried here. The model card's quality claims are self-reported with no independent reproduction checked, and this page makes no quality claim at all.

Vision

The upstream repository is image-text-to-text and ships mmproj-BF16/F16/F32 projectors as separate files. A catalogue row in Local Mind names exactly one file, so this entry is the text model; image prompting is not catalogued and was not tested.
