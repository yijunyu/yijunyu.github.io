  • DeepSeek-V4-Pro-Qwen3.5-4B — a 4B hybrid qwen3.5 derivative distilled from DeepSeek-V4-Pro on maths and STEM, with a decensored variant. On an M1 Ultra 128 GB it decodes at 104.2 tok/s and prefills 512 tokens at 1,552–1,619 t/s. Measured Provisional The weights were read from a USB volume on a host under memory pressure, so the entry keeps the catalogue's unevaluated badge: two conditions that rule names were not met. Decode is the more portable of the two figures — the file is resident after load, so the transfer path costs load time, not per-token time — while prefill's two runs differ by 4% and should be re-taken on internal storage.
  • Inkling-2-Mini — Thinking Machines’ 128x1.8B MoE whose 12-block core runs three times, so a forward pass performs 48 layer visits; a 17.63 GB IQ4_NL GGUF and a 17.33 GB MLX 4-bit pack are catalogued. Catalogued, not measured Our pinned llama.cpp has no inkling2_loop architecture; upstream merged it in PR #32694, and an upstream build (225a534) does run the family. Measured On that build the uncensored IQ2_M quant decodes at 25.3 tok/s and prefills 512 tokens at 459 t/s on an M1 Ultra: llama-bench, 3 repetitions, ±0.34 and ±3.07, fully offloaded, one process rather than the three the other rows use, at llama-bench's default context rather than the model's 1M. Its IQ3_S and Q4_K siblings are catalogued and NOT measured. It is not the same model as Inkling Small, a separate 42-layer 256-expert architecture. The upstream weights are measured too (2026-11-22): on unsloth’s 8.49 GB UD-IQ2_XXS, the same llama.cpp build gives 16.2 tok/s on an M4 mini and 14.3 on an M1 Ultra, where that file is 1.8× slower than the AD-IQ2_M one in the same window. Measured Strata 0.2.19, which added this model, gives no usable rate on either Mac yet: every reply is token id 0 on the M4, and its Metal kernels do not compile on the M1. Catalogued, not measured A further engine option is Atomic Engine, an MIT-licensed llama.cpp fork that runs AtomicChat’s AD-IQ2_M, AD-IQ3_S and AD-Q4_K GGUFs under an 8–20 GiB engine budget with SSD expert streaming and a 0.5 GB Q8_0 DSpark draft; see Inference engines. Its publisher claims 105.7 tok/s decode for AD-IQ2_M at 14 GiB on an M4 Max against 33.1 for stock llama.cpp; that is an upstream claim, not a rate measured on any machine here.
  • Qwen3.5-9B Defiant — a 9B dense qwen3.5 hybrid fine-tune with an MTP layer, measured on the exact catalogued MTP-Q4_K_M file. Measured Provisional On an M1 Ultra 128 GB it decodes at 42.5 tok/s (41.8–46.1 across three separate processes at the default thread count) and prefills 512 tokens at 888 t/s. The host was not idle and the same file at -t 8 measured 54.0 tok/s, so the decode figure is a floor rather than a quiet-box rate.
  • Maxwell-V1-Flash — a 35B-A3B mixture of experts, 45 layers, 256 experts at 12 active. Measured Provisional No llama.cpp has its architecture, so it ran through the publisher’s own reference code: 0.17 tok/s decode, 0.2–0.3 t/s prefill. Measured twice, at 19.4 and 39.8 GiB of available memory, agreeing to 4% — so the rate is the path, not the host, and about 100× below what the hardware allows. That first explanation (paging) was wrong and the re-measurement is what showed it. Its file also declares the same 4 hyper-connection streams and the same 20 Sinkhorn iterations as the DeepSeek-V4.1-Flash export this site’s engine runs.

How to read availability on these pages

Every page says plainly whether something is in a released build, in a TestFlight build, or only on a development branch. These are three different things and the pages do not blur them. A feature described as in development is not available to download, and no date is promised for it.

Likewise, no page quotes a speed figure without naming the model and quantisation, the machine, the storage the weights were read from, the engine and the context length, and saying how it was measured. Where a figure in the app is modelled rather than measured, the page says so.
