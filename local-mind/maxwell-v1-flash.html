The model works. What the figure does not measure is the model.

What I first reported here was wrong, and the second run is what showed it. The first figure, 0.172 tok/s, was taken while another process held 46.2 GB and about 0.1 GiB was free, and this page said the rate was therefore a paging floor that a quiet box would replace. A quiet box was then arranged — the re-run waited for 39.8 GiB of reclaimable memory to hold across two polls — and it measured 0.165 tok/s, 4% slower, over 32 tokens instead of 8. Doubling the headroom moved the rate by nothing. The constraint is not memory.

What the constraint is, then, is the path: the publisher’s Python modelling code with auto-round’s MLX backend, which is a correctness reference and not a serving engine. For scale, a token of this model reads on the order of 6 GB of weights; at a modest 100 GB/s that is 60 ms, and the measured step is 6,059 ms — about 100x more. Nothing here says the architecture is slow. It says this way of running it is, and a llama.cpp that knew maxwell_moe would be the instrument to ask.

Why the reference implementation, not an engine

No llama.cpp has this architecture. The community GGUF conversions declare maxwell_moe (end000) or maxwell-moe (AtomicChat) — two spellings of something neither the installed build 10964 nor upstream master (5297534, checked 2026-11-18) contains. The checkpoint ships its own modelling code with an auto_map, so the path that exists is the publisher’s Python, not a serving engine. That is a different instrument from every other row on this page, which runs llama.cpp, MLX or the reference CUDA engine, and it is named here rather than left to be inferred from the missing engine column.

The part worth recording: it shares DeepSeek-V4.1's mechanisms

Three mechanisms in this model appear in the DeepSeek-V4.1-Flash engine this site's own campaign runs. The values below were read from each model's own file header, not from either card:

MechanismMaxwell-V1-FlashDeepSeek-V4.1-Flash (the Coder export this site runs)
Hyper-connections4 streams, 20 Sinkhorn iterations4 streams, 20 Sinkhorn iterations — identical on both
Sparse attention indexer4 heads, 128-wide, 128-token blocks, top-16 of 32 blocks32 heads, 128-wide keys, top-512
Routingsigmoid score, per-expert bias, gating enum 2per-expert bias, gating enum 4
Shape2,048 hidden, 45 layers, 256 experts at 12 active, 512-wide experts5,120 hidden, 40 layers, 192 experts at 6 active, 2,304-wide experts

The hyper-connection row is the striking one: the same number of residual streams and the same Sinkhorn iteration count, which is a parameterised decision rather than a coincidence of naming. The rest differs on every axis a kernel cares about — 45 layers against 40, 2,048 hidden against 5,120, 256 experts at 12 active against 192 at 6, 512-wide experts against 2,304-wide, and an indexer with 4 heads against 32.

Shared mechanisms is not a shared architecture. A kernel written for one will not run on the other; what transfers is the shape of the problem, not the code.

What that makes it is a candidate, and the honest statement is narrow: if an engine for this mechanism set is ever written here, the 19.36 GiB quantisation fits whole in a 128 GB machine's GPU with room to spare — the opposite of the 182.7 GiB DeepSeek-V4.1 Coder export this site streams from an SSD. Until such an engine exists, the row reads not measured.

What is not claimed

No rate for the bf16 checkpoint, and no serving-engine rate at all. The publisher reports that its MBSA kernel is 6.7× faster than dense grouped-query attention at 256K, and vendor benchmarks for the model itself (AIME 2025 96.25 mean@8, GPQA-Diamond 86.52, LiveCodeBench v6 85.66, RULER 95.81). Those are the publisher's numbers on the publisher's engine, not measurements here, and none of them was reproduced.

This entry also makes no claim that DeepSeek-V4.1-Flash and Maxwell-V1-Flash are related codebases or share weights. The claim is only that the three named mechanisms appear in both, read from each one's configuration file.
