Strata 0.2.9 on the M1 Ultra

Strata's Mac support is new, and its manual is explicit about the evidence behind it: measured on an M5 Max with 128 GB, an M4 mini with 32 GB and an M1 Max with 34 GB — “Other chips are untested, and reports help.” This is the report for a fourth machine. It covers what the installer verified, what the engine did on a chip its manual does not cover, and the number it produced — together with the comparisons that number does not support.

Answer — governing thought

0.2.9 installs, verifies and runs on the M1 Ultra first try: 51.0 tok/s on a short request, 47.2 on a 200-token story, 530 t/s prefilling 4K–16K, and 12 of 12 sanity checks. It is a compatibility result and a new data point, not a verdict on the release's M5 Max figures — and on this chip the draft layer that is worth 27% upstream is worth nothing.

Integrity Everything the release published about itself checks out — hashes, notarization, and every file inside the engine package. ›
I1
Four macOS artefacts, four matching SHA-256s. The DMG, the 0.1.55 Control tarball, the 0.1.55 Metal engine and the DeepSeek 0.1.55 Metal engine were hashed against the release's own SHA256SUMS.txt: 4 of 4 OK. The Terminal's own installer then re-fetched Control and reported “Checksum ok” and “Signature ok” against the signed feed.
I2
The app is genuinely notarized. stapler validate: “The validate action worked”. spctl: accepted, source=Notarized Developer ID, origin=Developer ID Application: Niko Veit (79LR4R7RSC). codesign --verify --deep --strict: valid on disk, satisfies its Designated Requirement. Bundle version 0.2.9.
I3
The engine package can be checked file by file, and was. Its engine-component.json carries a SHA-256 and a byte count for each of 37 files — binary, Metal kernel sources, vision reader — and all 37 matched. The component is signed (ed25519, key id 5d1bc23abbeffd0d), build id 4cf0d8cd3809+metal.
I4
Versions agree end to end: app 0.2.9, Terminal strata 0.2.9 (build 0.1.55), engine strata 0.1.55-metal, Control 0.1.55 at commit 4cf0d8cd3809.
Compatibility It starts on the untested chip — and the engine picks the older kernels on its own, which is the right answer here. ›
C1
No workaround was needed. The engine logs GPU 0: Apple M1 Ultra, compute capability 0.0 and session is up (engine 0.1.55-metal). The decode window wrapped in 2.8 s. The first start in the session was answering within 45 s; two later starts were ready in 8.2 s each, which is what a cached Metal kernel compile looks like.
C2
The kernels are the M1 path, not the M5 path. prompt kernels ... the older expert / attention kernels (no M5 layout). The manual says the M5 prompt-expert layout “fails on an M1 Max”, so this is the engine declining a layout it knows is wrong — the reason a compatibility run on this chip can pass where a forced setting would not.
C3
Memory is not the constraint at this size. IQ3_S maps 54.8 GB and the engine reported 48,631 MiB of VRAM free with everything loaded, of a 107.5 GB Metal working set. The manual's larger packs (UD-Q4_K_XL, 82.6 GB mapped) should also fit, but were not run here.
C4
Storage is a bigger variable than any engine setting we touched. An earlier, unintended start ran the model from an external volume: the engine warned --ple-io direct measures slow here (517 rows/s, about 2 MB/s of random 4 KiB reads) and the decode window took 149,604 ms to become ready. On the internal SSD the same class of file wrapped in 2.8 s. The manual's “the model's file must be on the internal SSD” is not a preference.
Speed 51 tok/s short, 47.2 on a 200-token story, 530 t/s prefilling — and 12 of 12 checks correct. ›
S1
The standard suite (strata bench run, frozen fixtures, fresh process, three repetitions, thinking on, 512-token cap): short request 51.0 tok/s (51.0–51.1) with a 0.75 s first token; a 4K prompt at 528.9 t/s and 49.4 tok/s; a 16K prompt at 530.4 t/s and 46.5 tok/s. All six long-prompt requests reached the cap, so those decode figures are taken at the cap rather than at an answer.
S2
A fixed 200-token story, greedy, is the closest thing here to the manual's “story” column: 47.0 and 46.6 in two fresh processes, 47.4 and 47.6 in one warmed one — a median of 47.2 tok/s and a spread of 46.6–47.6. The first request after a start measured 38.0, so a cold number is a different claim.
S3
A 32,000-token prompt read at 525.5 t/s and decoded at 40.9 tok/s at that context; a 11,009-token prompt read at 511.3 t/s. Prefill is flat from 4K to 32K, which is what a prompt path that is not cache-starved looks like.
S4
Throughput is not the only result: the suite's twelve correctness checks passed 12/12 — instruction following 4/4, retrieval 4/4, tool calls 4/4 — and the Anthropic /v1/messages route returned 200 from a separately started server of the same build. A fast engine that cannot call a tool would not be worth this page.
Comparison The comparison a reader wants — against the 30.8 tok/s llama.cpp row on this machine — cannot be made on equal terms. ›
X1
The files are different, and so are the engines and the instruments. This box's Qwen3.8-Flash-Next row is llama.cpp's tg128 on Unsloth's UD-Q2_K_XL, 78.9 GB. Strata ran its own IQ3_S, 54.8 GB mapped (plus a 28.8 GB n-gram table), and the number is the server's own predicted_per_second at 200 tokens. 47.2 against 30.8 is 1.53×, and it is a statement about this pairing, not a like-for-like win: a smaller file is faster for any engine, and llama-bench is not this instrument.
X2
The same pack on the manual's M5 Max reads 94.7 tok/s on a story with MTP (74.8 without). The M1 Ultra's 47.2 is about half that, on a GPU with fewer, older cores — a plausible gap, and not something this run can attribute further. The release's headline Mac numbers are M5 Max numbers; nothing here confirms or refutes them.
X3
What a real head-to-head would need: one file both engines can read, on the internal SSD, with the same prompt and token count, repeated as whole runs. Strata's packs are its own quantisation and llama.cpp cannot read them; Unsloth's shards need Strata's source-installer repack, which the Terminal does not do. That experiment was not run.
Drafting The draft layer is worth 27% upstream and nothing here — measured, not inferred. ›
D1
MTP on (setup's default, --spec 2): 47.0, 46.6 tok/s on the story in two fresh processes, 47.4 and 47.6 in a warmed one. MTP off (no --spec, no --mtp): 45.8, 47.3, 47.2, 47.4 and 47.6 over five requests. The two ranges overlap and the medians are within 1% of each other; on this chip the draft layer does not pay.
D2
The manual reports the opposite on the M5 Max: 94.7 with MTP against 74.8 without for the same IQ3_S pack — +27%. So the feature is not inert in general; it is inert here, and the difference between the two machines is the finding.
D3
We did not isolate why, and do not claim a mechanism. A plausible candidate is that decode on this chip is bound by moving expert weights rather than by the arithmetic drafting skips; that was not tested, so it stays a hypothesis.

Caveats that travel with the number

The standard-suite figures are repetitions inside one process. The story figures were repeated across two fresh processes (47.0 and 46.6), which is the method this site prefers, but the suite's three repetitions of each prompt length share one load. A single run's error bar would understate run-to-run variation; the 4K prompt rate already spans 473.6 to 529.2 within the suite.

Context was configured at 64K and measured to 16K. The suite measured 16K, one manual prompt measured 32K, and the weights themselves declare 262,144 positions. Nothing above 32K was run, and the manual's own measured ceiling is 32K.

Pictures were not tested. The engine package carries strata-vision, but the picture reader was not installed with the model (images: false), so every number here is text only.

One request at a time. The Mac engine does not port --parallel; every request was serial, and no concurrency result exists for this machine.

The machine was not quiesced for the suite. It was in ordinary desktop use; no GPU load was reported, but a busy machine can halve a number, which is why spreads are quoted.

Release integrity is a snapshot. The hashes, the notarization ticket and the engine manifest were checked on 2026-10-31 against release v0.2.9; a later rebuild of the same version would not match them, and that is the point of recording them.
