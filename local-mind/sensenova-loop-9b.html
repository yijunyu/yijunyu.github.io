Status: catalogued, and it will not load. The weights are on disk here. No speed figure is quoted, because neither public Q4_K_M conversion can be opened by the installed engine — and the two fail for different reasons, both read off the loader rather than inferred.

A 9B multimodal model from SenseNova, published 2026-11-17. Its distinguishing feature is architectural: 32 layers, of which 24 are executed twice, so a forward pass performs 56 layer executions from 32 layers of weights. That is a compute-for-memory trade — a 9B file costs about a 14.6B model's arithmetic, which the card itself calls "inference-equivalent 14.6B".

Why it does not load: two conversions, two failures

The interesting part of this entry is that "the GGUF is broken" is not one fact. Two public Q4_K_M conversions of the same model fail against llama.cpp build 10964, and the loader's own messages separate them:

ConversionDeclared architectureWhat the loader said
AtomicChatqwen35wrong number of tensors; expected 523, got 427
annelosensenova_loopunknown model architecture: 'sensenova_loop'
guideboardlabssensenova_loopunknown model architecture: 'sensenova_loop'

The first two rows were measured here on 2026-11-18 — both files are on disk and both loader messages are quoted from runs against them. The guideboardlabs row is a third conversion carrying the same architecture name, reported by the same loader at an earlier attempt; that file was deleted from disk once the AtomicChat one showed qwen35 was the more promising label, so its message is not re-verified in this write-up.

The second and third are the honest case: the converter wrote the model's real architecture name, and upstream llama.cpp has no such architecture — the installed runtime's architecture list carries no sensenova* entry at all, so these files need an engine change, not a flag.

The first is the one worth understanding. AtomicChat's file declares qwen35 — an architecture the engine does support — and the header parses cleanly all the way through its 48 metadata keys and its context length. It fails later, at tensor mapping, because the file carries 523 tensors where qwen35 expects 427. The 96 extra are the mhc_attn.* and mhc_ffn.* hyper-connection weights, four per reused layer across 24 layers. So the conversion took a qwen3.5-shaped stack and bolted the loop mechanism on without extending the architecture definition to define it.

This is why the entry is catalogue-only and why it should not be read as "the model does not work". A 9B model of this shape would fit on this machine many times over; what is missing is an engine that implements its architecture, not memory or disk.

What has been verified

  • The metadata parses. Architecture, 32 blocks, 4,096 embedding, 16 heads, 4 KV heads, 262,144 context, Apache 2.0 — all read out of the GGUF header directly, without loading the model.
  • Two conversions were loaded here and failed; a third reports the same architecture error. The two failure modes above are the complete set: one architecture mismatch at the tensor table, and one architecture the engine does not know.
  • The tensor inventory is the reason the first file fails. Comparing its suffixes against a known-good qwen35 file (see DeepSeek-V4-Pro-Qwen3.5-4B) shows the 24 shared suffixes plus mhc_attn and mhc_ffn and nothing else — the extra 96 tensors exactly.

What is not claimed

No decode or prefill rate, measured or modelled. The loop mechanism makes an obvious projection tempting — 32 layers of weights but 56 layer executions, so a decode rate lower than a plain 9B by roughly the ratio of executions to layers — and that projection is not used here. It would be a claim about a model no engine here can run.

Also not claimed: that a fixed conversion is close. Someone would have to add sensenova_loop to an engine, or produce a GGUF that expresses the loop within an architecture the engine already has. Neither exists today, and this entry will be replaced with a measurement if one does.

Engines

None here loads it. The publisher ships an official AWQ 4-bit release and points at llama.cpp, LM Studio and Jan, but the GGUF conversions those tools consume are the ones that fail above — so the recommendation is real for some future conversion and not for the files currently published.
