DeepSeek V4.1-Flash is a 748B-parameter mixture-of-experts model with 16B active per token. It is far larger than any Mac's memory, so it is read from storage as it runs rather than held resident, and that makes the size of the weight file the thing that matters most.

Nine community quantisations, and what they cost

The quantisations published for this model range from about 217 to 474 GiB. Smaller is not merely cheaper to store: on a machine that streams the weights, fewer bytes per token is the dominant term.

Why reading them took work

This model carries an n-gram memory — a very large lookup table consulted per token, separate from the transformer weights. In these exports it is a single tensor of 768,022,850 rows that lives alone in the last shard, while the constants describing how to index it live in the first shard. A loader therefore has to carry a description read from one file to a table held in another.

Local Mind already decoded this model from its own weight export. What was missing was that the community exports spell the same indexing constants under different names. They are now read under both spellings, so a file written by either converter loads.

One detail worth recording, because it is the kind of thing that passes review and then fails quietly: the row count of each half of the table could be computed two ways — from the stored offsets, or by summing the bucket sizes. The loader checks those two against each other, so it deliberately reads one of them rather than deriving it from the other. A check whose two sides come from the same number cannot fail.

What has been verified

  • The 5-shard 217 GiB export opens from its first shard and exposes all 1043 tensors, the count the file itself declares.
  • The indexing constants yield table halves of 384,006,168 and 384,016,682 rows, which sum to exactly the 768,022,850 rows the table has — three independent sources agreeing.
  • Rows read at real computed indices decode to finite, plausibly scaled values, and a read one row past the first half is refused rather than silently returning the second half's data.
  • A whole token decodes through all forty layers, four positions in sequence, with caches growing across positions. The predicted token agrees with a reference dump recorded on a different quantisation of the same model at 3 of 4 positions.
  • Three independent checks confirmed the result does not depend on internal scheduling choices: doubling a writing kernel, chaining stage boundaries, and recycling the output buffer pool each left the output unchanged.

What is not claimed

No decode or prefill speed. The run above was a single bounded walk of four positions on a shared machine, using an instrument built to check correctness rather than to time anything. It is not an end-to-end serving measurement, it has no repetitions, and its own documentation expects a very different per-token cost than was observed — which is reason to understand the instrument better before quoting any rate from it, not reason to quote the faster number.

Not parity. Agreement at 3 of 4 positions is cross-quantisation agreement with a differently-built export, and the test deliberately asserts no threshold: the correct agreement rate between two different quantisations is not known in advance, so any threshold would be a number chosen to pass. The position that differs is the first one, where there is no preceding context.

Not an offering. None of these weight files is in Local Mind's catalogue, and nothing here says the app will download or serve them.
